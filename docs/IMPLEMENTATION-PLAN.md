# 财神主题实施计划

发布归档：六阶段与视觉修复汇入 `0.2.0`。下文按开发阶段保留验收时点；当前实现与发布结果以验证记录顶部为准。

本计划对应 [需求清单](REQUIREMENTS.md)，按“保持行为的结构整理—数据保护—常用工作流—视觉完善—可选扩展”分步推进。更新日期：2026-10-23。

## 当前阶段与执行原则

- 阶段 1 至 6 已完成；本轮补齐项目库、功德簿、宿主适配与 DSH `0.2.1-rc.2` 隔离安装、启停、卸载，结果见 [验证记录](VALIDATION.md)。
- 第六阶段的探索任务已完成评估和独立后续计划；成本、效率及云同步未进入当前主题。
- 每阶段先检查依赖，再实施、验证和记录结果；新的用户可见行为单独交付，避免和纯迁移混在一起难以评审。
- 保持现有包身份、DSH loader 包装、九个插槽和原 localStorage key；新增字段、偏好 key 与中英文文案须明确记录兼容方式，不扩大宿主兼容版本范围。
- 自动检查使用 mock 和隔离存储；真实 DSH 验收使用独立测试环境，不操作日常会话或真实卡片。

## 目标目录

以下为本轮的目录职责，不要求每项职责都单独建立一个只有几行内容的文件。最终文件名以实际模块边界为准。

```text
.
├── src/client/              # 手工维护的标准 CommonJS .cjs 模块，入口 index.cjs
│   └── styles/              # 十五份独立 CSS 与样式 link 安装模块
├── src/host/                # 手工维护的宿主 ESM 源码
├── lib/
│   ├── client.js            # 已提交的构建产物，保留 DSH loader 单入口契约
│   ├── client.css           # 按原级联顺序生成的独立 CSS
│   ├── host/                # 由 src/host/ 复制的生成模块
│   └── index.js             # 薄导出，转发生成的宿主入口
├── assets/
│   ├── runtime/             # 当前运行时实际引用的图片、图标和纹理
│   ├── source/              # 可重新编辑或导出的原始素材
│   ├── archive/             # 不再使用的旧版与备选素材
│   ├── application/         # 插件管理页图标与可选程序坞图标
│   └── previews/            # 经筛选的文档截图和预览图
├── reference/               # 配色等参考资料，不作为第二份运行真值
├── scripts/                 # 构建、产物一致性、离线及打包检查
└── docs/                    # 需求、计划、开发、素材、发布和验证记录
```

`assets` 迁移后，既有 `/theme-caishen/assets/*` 与 `/theme-caishen/extra/*` 路由均解析到 `assets/runtime/`，后者作为兼容别名保留。新增 `/theme-caishen/styles/client.css` 只提供 `lib/client.css`。旧新文件路径、用途和哈希记录在 [素材清单](../assets/manifest.json)，包导出、文档截图和参考文件链接同步更新。

## 阶段 1：拆分源码并整理资源

**状态：结构整理完成，实机验收待验证。对应：BASE-001 至 BASE-007、ENG-001 至 ENG-007。**

阶段 1 交付时落地 18 个客户端 CommonJS 模块、7 份独立 CSS、宿主源码和零依赖构建。客户端源码入口保持为连接各模块的短入口；`lib/client.js` 仍是单个自动生成的 DSH loader 产物，后续修改应在 `src/` 中完成。

独立对照确认：归一素材 URL 后，九个插槽及代表性组件分支的 DOM/props 保持一致；主题 token 与中英文键值相同；CSS 去除注释与空白后按级联顺序等价；迁移图片和配色参考的二进制内容保持一致。两次隔离构建产物字节一致，修改 CSS 后 `check:build` 能拒绝过期产物且不覆盖文件。离线检查和打包检查通过，真实 DSH 安装与新产物视觉验收仍待验证。以下步骤保留作为本阶段的实施与复验顺序。

### 步骤 1：建立迁移基线

1. 记录客户端包身份、导出、主题 token、中英文文案、九个插槽与注册选项。
2. 盘点 JS、CSS、模板、状态和宿主适配逻辑，确定模块边界。
3. 查明每张图片的实际引用、原始版本、历史版本和文档用途；建立旧路径到新路径的对应关系。
4. 保存现有检查结果和验证边界；将草稿覆盖问题登记为 SAFE-001，不在结构整理时静默修复。

验收：迁移有明确的比较对象；未把文件存在误认为正在使用，也未将已知问题列为本轮修复成果。

### 步骤 2：拆分客户端 JS

1. 把手工维护源码移入 `src/client/` 的标准 CommonJS `.cjs` 模块，分别整理配色、文案、工具、状态、组件和 `apply` 注册；依赖使用静态 `require()`。
2. 保持函数语义、数据校验、组件状态、插槽选项和 effect 清理逻辑。
3. 由清晰入口组装模块，继续从宿主获取 React，避免引入另一份 React 或第三方运行依赖。
4. 保留检查脚本使用的导出，以便继续验证默认模板、卡片校验、排序与存储。

验收：不存在缺失模块或隐式全局依赖；默认卡片、文案、存储格式与插槽清单可和原基线对照。

### 步骤 3：独立维护 CSS

1. 将模板字符串中的样式提取到 `src/client/styles/`。
2. 按基础、品牌、首页、提示词与弹窗、宿主适配、响应式等职责组织；保持原样式的先后顺序。
3. 按 `base`、`hero`、`cards`、`chrome`、`decorations`、`responsive`、`prompt-library` 的稳定顺序构建 `lib/client.css`；由插件添加样式 link，并在 effect 清理时移除。
4. 保留所有媒体查询、减少动态效果、浅深色覆盖和现有宿主选择器；视觉重设计留到后续阶段。

验收：同一基线下生成的有效样式行为一致；未因选择器重排改变响应式优先级。

### 步骤 4：建立构建与产物一致性检查

1. 通过 `npm run build` 原样包装客户端模块图，生成包含原 DSH loader 包装与模块 ID 的 `lib/client.js`，同时生成独立 CSS、`lib/host/` 副本和 `lib/index.js` 薄导出。
2. 通过 `npm run check:build` 只检查、不覆盖文件，发现未构建修改时提示重新构建；`check` 与发布检查先验证产物，不偷偷重建。
3. 在检查和发布流程中串联语法、模块契约、数据、素材与构建产物检查。
4. 保留构建产物到仓库，确保 Git 安装和打包安装无需在用户设备上编译。

验收：连续构建产物一致；修改源码但未构建可被检查发现；已构建状态可完成现有离线检查。

### 步骤 5：迁移素材与参考资料

1. 按用途迁移到 `assets/runtime`、`source`、`archive`、`application`、`previews`，保留必要原件和历史方案。
2. 统一配色参考到 `reference/`，标明运行 token 的维护位置。
3. 同步宿主路由的磁盘映射、客户端资源地址、包清单、导出映射和素材检查。
4. 同步 README、开发文档、素材文档、截图和程序坞图标的链接。
5. 确认运行包只携带必要资源及公开说明；保留 npm 自动纳入的 `assets/README.md` 索引；原稿、归档、截图与 Dock 图标保留在仓库，不夹带临时输出或个人环境文件。

验收：所有运行引用和文档链接可解析；重定位打包后图片仍可读取；原始大图和历史资源不构成运行依赖。

### 步骤 6：完成验证与交付记录

1. 执行构建、产物一致性、离线检查和打包检查；检查包文件清单和素材路由的 GET/HEAD 行为。
2. 对照九个插槽、主题 token、中英文键值、默认卡片和存储 key，确认结构迁移未改变既有契约。
3. 对新旧会话、浅深色、窄窗口、较矮窗口、提示词弹窗及功德按钮进行适当预览；只能报告实际完成的检查。
4. 更新开发和发布步骤，写明源码与产物的关系及新的素材目录职责。
5. 记录真实 DSH 安装验证是否完成；未执行则保留待验证项，不自动发布。

阶段出口：ENG-001 至 ENG-007 的结构整理已完成，后续功能仍标记待实施；新构建产物的真实 DSH 安装与视觉验收保留待验证，由交付和验证记录列出实际结果与限制。

## 阶段 5：补项目范围与可选趣味功能
